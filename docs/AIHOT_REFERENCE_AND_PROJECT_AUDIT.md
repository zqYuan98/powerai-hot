## 2. AI HOT 的产品模型

### 2.1 内容结构

AI HOT 的核心不是门户首页，而是高频更新的 AI 阅读流：

1. 聚合来源内容，统一成标题、摘要、来源、时间和主题标签。
2. 通过“最新、热门、精选、分类”等入口降低筛选成本。
3. 用户在主列表快速扫读，点击条目进入详情或原始来源。
4. 桌面端强调侧边导航与主阅读区，移动端用底部导航和局部弹层保留主线。
5. 产品价值来自持续更新、筛选质量和阅读效率，而非复杂表单。

### 2.2 信息架构

```text
AI 信息源
  └─ 聚合与整理
      ├─ 最新/热度/精选
      ├─ 分类与标签
      └─ 单条详情/外链
          └─ 用户继续阅读、收藏或分享
```

其信息架构的关键原则是“阅读优先”：导航承担切换，主区域承担内容，辅助信息按需出现。桌面端不会让多个操作面板长期争夺正文宽度；移动端会把低频功能折叠，而不是缩小桌面布局。

### 2.3 交互方式

- 列表卡片适合快速扫描，视觉层级由标题、摘要、元信息构成。
- 分类切换保持在当前阅读上下文，反馈直接。
- 移动端底部导航贴合单手操作，详情/筛选采用局部覆盖。
- 交互控件具备明确点击目标，主阅读路径不被后台配置能力打断。

对本项目最值得继承的不是视觉皮肤，而是三点：阅读优先、渐进披露、移动端重新编排。

## 3. 当前项目架构

### 3.1 数据与任务链路

```text
北极星 / RSS / arXiv / HF Papers
  ↓ 采集与规范化
URL 去重与文章入库
  ↓
规则预筛 → AI 评分 → 内容富化 → 向量/卡片
  ↓
事件聚类 → 日报 / 收藏 / 研报 / 订阅推送
  ↓
FastAPI → Next.js 前端
```

## 5. 验证证据

### 5.1 可用性基线

2026-07-11 整改后：后端 **284 passed**；前端 **72 passed**；门户 **5 条 Playwright E2E**；Next.js 15.5.20 生产构建通过；`npm audit --audit-level=moderate` 为 0。ESLint exit 0，保留 6 条既有 warning。移动端整改后于 390/768/1280 视口实测无页面级横向溢出。

2026-07-10 整改前：

- 后端：`python -m pytest -q`，**141 passed**，耗时约 1.97 秒。
- 前端：`npm.cmd run build` 成功；首页首屏共享资源约 128 kB，文章详情约 101 kB。
- 浏览器：桌面端主模块可加载，未观察到控制台错误。
- `npm.cmd run lint` 会进入交互式 ESLint 初始化，因此当前没有可执行的 lint 质量门禁。

### 5.2 性能与数据访问

本地真实接口抽样：

- `GET /api/articles` 一次返回 936 条记录。
- 响应约 1,528,109 UTF-8 字节，单次本地请求约 380 ms。
- 前端当前无筛选参数调用该接口，并每 60 秒刷新一次。

这意味着单个长期开启的页面理论上每天可重复传输约 2.2 GB 文章 JSON，而且数据量会随入库持续增加。后端也会先取全部文章，再处理关联聚类计数；频道统计同样把文章 ID 读入 Python。分页和 SQL 聚合应进入最高优先级。

### 5.3 响应式与可访问性

在 390 × 844 视口下：

- 文档宽度约 1180 px，横向溢出约 790 px。
- 固定桌面侧栏仍占约 228 px，没有移动端抽屉或底部导航。
- 样式中未发现有效媒体查询。
- 多个筛选/导航使用带点击事件的 `div`、`span` 或无 `href` 的链接，键盘与读屏语义不足。
- 顶部“搜索情报、机构、关键词…”是样式化文本，不是真实输入框，尽管后端已有 `q` 查询能力。

### 5.4 依赖与运行环境

- `npm audit` 报告 2 个漏洞：Next.js 直接依赖为高危，PostCSS 为中危。
- Python 测试有 Pydantic 旧式 `Config`、Starlette/httpx 和 pytest-asyncio 配置警告。
- 当前审计环境为 Python 3.13，项目目标为 Python 3.11，且没有隔离虚拟环境；全局 `pytest-asyncio` 与 `pytest` 版本约束不一致。
- 环境中没有 `pip-audit`，因此本次没有声称完成 Python 依赖漏洞扫描。

## 6. 风险与优化优先级

### P0：已完成的生产基线整改

#### P0-1 管理令牌会暴露给浏览器（已解决）

main 已删除浏览器端 `NEXT_PUBLIC_ADMIN_TOKEN`/绝对 API 基址，改用同源 HttpOnly 签名会话；E2E 覆盖 workspace/admin 和篡改 cookie 后重新锁定。

建议：引入服务端会话/SSO，或通过 Next.js BFF、可信网关保存管理凭据；前端只持有用户会话，不持有后台总令牌。

#### P0-2 写接口权限不完整（已解决）

main 的 workspace/admin 访问矩阵已覆盖业务写接口和管理操作，匿名访问回归测试保持 401。

建议：建立统一身份和权限矩阵，对全部写操作默认鉴权；只把明确设计为公开读取的接口匿名开放。

#### P0-3 Compose 会启动双调度器（已解决，待 Docker 环境运行时复核）

默认 Compose 已删除 Celery worker/beat 与 Redis 依赖，只保留单实例 APScheduler，并提供 `scripts/verify-compose.ps1` 检查 next_runs 与容器进程。当前开发机没有 Docker CLI，因此容器运行时复核必须在发布环境执行。

建议：生产统一采用 Celery 时强制 backend `AUTO_CRAWL_ENABLED=false`；或删除 Celery beat，只保留单进程 APScheduler。增加“同一任务时间窗只执行一次”的集成测试或分布式锁。

#### P0-4 前端依赖存在高危公告（已解决）

已升级 Next.js 15.5.20、PostCSS 8.5.16、Vitest 4.1.10，并通过单测、E2E、生产构建和 `npm audit --audit-level=moderate`（0 vulnerabilities）。

### P1：一周内完成，直接改善体验和成本

#### P1-1 文章分页、游标和服务端筛选（已解决）

为 `GET /articles` 增加 `limit`、游标/页码、频道、时间、精选、噪声和排序参数；返回 `items + next_cursor + total/has_more`。频道数使用 SQL `GROUP BY`。前端只请求可视数据，刷新时增量合并。

目标：首屏文章 API P95 < 300 ms、压缩响应 < 200 kB，后台静置 10 分钟不重复下载全量数据。

#### P1-2 真正的搜索（已解决）

把顶部占位文本替换成可聚焦输入框，接入现有 `q` 参数，支持回车、清空、加载/空结果、URL 状态和 300–500 ms 防抖。后续再升级全文检索，不必阻塞第一版。

#### P1-3 移动端重新编排（已解决，2026-07-11）

已实现：≤768px 视口隐藏固定侧栏、员工/管理双壳提供底部主导航；需求池改为可关闭的底部抽屉（FAB 入口）；频道 Tab 与筛选条横向滚动；热点/卡片单列；研报、知识中心、流水线多栏页面移动端上下堆叠。浏览器实测 390/768/1280 视口信息流、详情页与管理端均无页面级横向溢出，底部导航点击目标 ≥44px。原始要求保留如下以便追溯：

不要等比例缩放桌面三栏：

- 小屏隐藏固定侧栏，提供底部主导航或抽屉。
- 需求池改为可关闭的底部抽屉。
- 筛选条允许横向滚动或折叠为筛选面板。
- 卡片保持单列，点击目标至少 44 × 44 px。

目标：390 px 视口无页面级横向滚动，核心信息流、搜索、收藏、日报均可单手操作。

#### P1-4 建立前端质量门禁

补齐非交互 ESLint 配置、格式检查和最小组件/端到端测试；CI 至少执行后端测试、前端 lint、类型检查、构建和依赖审计。合并重复的 `next.config.js`/`next.config.mjs`。

### P2：一到两个迭代，提升可维护性

#### P2-1 正式迁移与数据库索引

当前轻量迁移主要靠 `ALTER TABLE ADD COLUMN`。引入 Alembic，补充对 `crawled_at`、频道、精选/评分、噪声、`cluster_id` 等高频过滤字段的组合索引，并用真实数据量查看执行计划。

#### P2-2 可靠后台任务

手工触发仍依赖 FastAPI `BackgroundTasks` 或线程，进程重启会丢失任务。统一进入持久队列，记录幂等键、重试次数、错误分类和任务耗时。

#### P2-3 前端组件化与设计系统

`SourcesModule`、`PipelineModule` 等文件已经较大，且大量使用内联样式。按“查询状态、展示组件、编辑表单、运行监控”拆分，建立颜色、间距、字体、状态和断点 token，减少模块间视觉漂移。

#### P2-4 内容质量与可观测性

建立固定的标注集，跟踪预筛召回、精选准确率、噪声率、聚类纯度、日报覆盖率、单条模型成本和人工采纳率。生产观测应覆盖采集成功率、队列积压、模型延迟/错误/费用、推送结果和数据新鲜度。

## 7. 建议实施路线图

| 阶段 | 时间建议 | 交付结果 |
|---|---|---|
| 安全止血 | 1–2 天 | 不泄露令牌；写接口统一鉴权；Compose 只运行一个调度器；Next 安全升级方案落地。 |
| 体验与性能 | 3–7 天 | 分页/搜索与前端质量门禁已完成；移动端主路径仍待专项优化。 |

## 8. 验收标准

完成本轮优化后，至少满足：

- 浏览器构建产物和网络请求中不存在后台总令牌。
- 未登录用户不能调用任何非公开写接口。
- 同一周期任务只有一个执行者，重复任务率为 0。
- `npm audit` 无未接受的高危漏洞；Python 依赖在隔离的 3.11 环境中可复现安装和扫描。
- 后端测试、前端 lint、类型检查、构建和关键 E2E 在 CI 中自动运行。
- 390/768/1280 px 视口均无页面级横向溢出，键盘可操作主要导航和筛选。
- 文章列表使用分页/游标，首屏不再下载全库数据。
- 搜索是真实输入，查询状态可分享/返回，空结果与错误有反馈。
- 关键采集、模型、队列和推送指标有仪表盘与告警阈值。
